# rules_trivy — design notes

rules_trivy runs Trivy scans as Bazel tests, answering the [package request](https://github.com/collider-bazel-extensions/.github/issues/2). Like rules_gitleaks, it wraps a CLI scanner rather than a service, and it takes rules_gitleaks' conventions:
- a binary toolchain pinned from published checksums;
- a host-Python driver that stages inputs and decides the verdict;
- analysis tests and functional fixture tests;
- `tools/update_*.sh`;
- the README / DESIGN / CLAUDE.md set.

What is new for Trivy is the data it reads at scan time (the vulnerability DB, the Java DB and the checks bundle). Pinning that data as Bazel repositories, so no test touches the network, shaped most of the design.

## Decided

| # | Decision | Choice | Source |
|---|---|---|---|
| 1 | Bzlmod / WORKSPACE | **Bzlmod only**, module version 0.1.1. | Every sibling |
| 2 | Module extension | One extension, `trivy`, with four tag classes: `version` (the binary), `db`, `java_db`, `checks` (the data). rules_trivy's own tags are the base; the root module's override them **tag class by tag class**, so a root can bump the DB without restating the binary. Other modules' tags are ignored. Repeating an identical tag is fine; two different ones in one module fail, naming the tag. | rules_argocd v0.1.1 / rules_atlas#12 (own tags as base, root overrides) |
| 3 | Binary | The upstream release tarballs (`trivy_<ver>_{Linux-64bit,Linux-ARM64,macOS-64bit,macOS-ARM64}.tar.gz`), one static Go binary each. SHA-256s from the release's `trivy_<ver>_checksums.txt`, each cross-checked against the download by `tools/update_versions.sh` (`--check` re-verifies; CI runs it). Repos are unversioned (`trivy_<platform>`), each declaring its own `trivy_toolchain`, and download only when toolchain resolution picks them. | rules_gitleaks |
| 4 | Versions rules_trivy doesn't list | `trivy.version(version, sha256 = {platform: sha})`. For a listed version the shas replace its pins. A platform without a sha gets a repo that fails, naming `sha256`, only when fetched. An unlisted version without shas fails at resolution, naming `trivy.version`. | rules_argocd v0.3.0 (`argocd.version(sha256, cli_sha256)`) |
| 5 | How the data is pinned | By **OCI manifest digest**. `trivy_data_repo` downloads `/v2/<repo>/manifests/<digest>` with `sha256 = <digest>`, so Bazel verifies the bytes. It then reads the single layer's digest and media type from the manifest, and downloads `/v2/<repo>/blobs/<layer>` with that sha. Both are content-addressed, so they come from the repository cache when present, and the data is exactly what the digest names whichever registry serves it. A digest of the wrong kind of artifact (a Java DB digest given to `trivy.db`) fails on the layer media type. GHCR needs an anonymous bearer token (`https://ghcr.io/token?scope=repository:<repo>:pull`); fetching it is allowed to fail, since a cached download needs none. | — |
| 6 | Do old DB digests stay fetchable? | **Yes; no mirroring needed.** Checked on 2026-11-16 (details below). A pin therefore keeps working. `repository` on each data tag lets a consumer fetch the same digest from a mirror, and Bazel's `--downloader_config` can rewrite URLs. | Measured |
| 7 | DB layout and size | The DB layer (~140 MB) unpacks to `db/trivy.db` (~1.8 GB) + `db/metadata.json` in `@trivy_db`. A test links both into a Trivy cache directory in `$TEST_TMPDIR`, never copying them. Trivy opens the DB **read-only**: a scan against a `chmod -R a-w` copy works, so a test can't modify the pinned repository. | Measured |
| 8 | Java DB | Opt-in per test: `java_db = "@rules_trivy//:java_db"`. It is ~1 GB to download (~1.6 GB unpacked), so a test that doesn't name it doesn't fetch it (`//tests:analysis_tests_no_java_db`). Without it, an image with a jar makes Trivy fail outright (`'--skip-java-db-update' cannot be specified on the first run`); the test then says to set `java_db`. Same pinning as the DB. | Measured |
| 9 | Misconfiguration checks | The **trivy-checks bundle, pinned** like the DB (`ghcr.io/aquasecurity/trivy-checks:2`, the tag Trivy 0.76 reads). Trivy's embedded checks would also work offline: with `--skip-check-update` and no cached bundle it logs `ERROR Falling back to embedded checks` and scans. The embedded checks are pinned by the binary's sha and lag little (0.76.2 embeds trivy-checks from 2026-10-12; bundle v2.3.0 is 2026-10-14). The bundle was chosen anyway: the checks can then be bumped without a new Trivy, all three data artifacts work alike, and the run has no ERROR line. The bundle (~240 KB) stays packed in the repository and each test unpacks it into its cache directory. Unpacked files in runfiles would be symlinks, which the loader's directory walk could skip. | Measured |
| 10 | Offline, nothing implicit | Flags: `--skip-db-update --skip-java-db-update --skip-check-update --offline-scan --skip-version-check --disable-telemetry --cache-backend memory`. Environment: `HTTP(S)_PROXY`/`ALL_PROXY` set to `http://127.0.0.1:9` (a closed port), `NO_PROXY` empty, `PATH` an empty directory (go-getter shells out to git), `HOME`/`XDG_*`/`TMPDIR` under `$TEST_TMPDIR`, and every `TRIVY_*` variable removed. Trivy reads `trivy.yaml` and `.trivyignore` from its working directory and WASM modules from `~/.trivy/modules` by default, so the driver passes `--config ""`, `--ignorefile <checked file or "">` and `--module-dir <empty dir>`. This repository's tests run with `--sandbox_default_allow_network=false` (`.bazelrc`), and `network_blocked_test` checks it took effect. | rules_gitleaks "nothing implicit" |
| 11 | Terraform remote modules | Trivy downloads registry and `git::` modules to evaluate them, and has no flag to stop it. With the dead proxy and empty `PATH` the download always fails, so the result is the same with or without network. The test prints a `NOTE` naming the module, and the rest is still checked. Vendored modules (local `source`) are scanned. | Measured |
| 12 | Image input | `trivy image --input <path>`, which takes an OCI layout directory (`oci_image`) or a docker-archive tarball (`oci_load`'s `tarball` output group); both were tested. Two Trivy behaviours shaped the staging: **(a)** Trivy refuses a layout whose blobs are symlinks (`layout blob sha256:… is a symlink`), and rules_oci's layer blobs are symlinks to the layer tarballs. So the driver stages the layout as real files, hard-linked where it can (cheap even for large images) and copied otherwise. **(b)** With `--input`, Trivy **ignores `--platform` and scans an index's first image**, a silent wrong answer: an `oci_image_index` of a vulnerable amd64 and a clean arm64 image passed with `--platform linux/amd64`. So the driver resolves the index itself (nested indexes flattened) to the requested platform's manifest and stages an `index.json` naming only that one. A multi-platform index without `platform` is an error. | Measured |
| 13 | Config input | Trivy's directory walker **skips symlinks**: a directory of symlinked manifests reports `Detected config files num=0` and passes. As in rules_gitleaks, every input (tree artifacts file by file) is staged as a real file under its **workspace path** (`external/<repo>/…` for other repositories). Findings and an ignore entry's `paths` then name `deploy/rendered/x.yaml`, for generated files too. If Trivy recognises nothing in `srcs`, the test fails (exit 2) instead of passing having checked nothing. | rules_gitleaks staging |
| 14 | Ignore file format | Trivy's own **`.trivyignore.yaml` schema** (`vulnerabilities` / `misconfigurations`: `id`, `statement`, `expired_at`, `paths`, `purls`), so the file is familiar and plain Trivy can read it, with `statement` (the reason) and `expired_at` made mandatory. The alternatives were worse. A file format of our own (JSON or TOML) would be unfamiliar. A Starlark list of entries isn't a file and can't hold comments. | Trivy |
| 15 | Parsing it | The standard library has no YAML parser, and PyYAML would need rules_python or vendoring. The driver instead reads a **strict subset**: block mappings and lists, `[a, b]` lists, plain / single / double-quoted scalars, comments. Anything else (anchors, tags, `|`/`>` strings, flow mappings, tabs, stray indentation) is an error with its line number, never a guess. Scalars aren't typed (`2027-01-31` stays a string, then must parse as a date). It then validates the schema and reports every problem at once: unknown keys (with hints: `reason` → `statement`, `expires` → `expired_at`), missing or empty `id`/`statement`, a missing or impossible `expired_at`, and `secrets`/`licenses` sections (these scans don't report those). | — |
| 16 | Applying it | The checked, unexpired entries are written as JSON, which is YAML, and passed as `--ignorefile`, so Trivy applies exactly what was checked, with its own `id`/`paths`/`purls` matching. `expired_at` is dropped from that copy, since expiry is already enforced. An image scan's `--show-suppressed` output is printed per entry with its statement, and entries that matched nothing are noted. `trivy config` has no `--show-suppressed`. | — |
| 17 | Expiry | An entry expires at the start of its `expired_at` day, UTC, as in Trivy (`now.After(expired_at)`). Trivy itself just stops applying an expired entry, so the finding reappears and fails, which hides why. Here an expired entry fails the test (exit 1) whether or not its finding still exists, naming the entry and its statement. **A cached pass does not notice expiry:** the date isn't a test input. Making every scan uncached (`external`) would re-run them all on every `bazel test`, so the README recommends a scheduled `--nocache_test_results` run instead. A DB bump also changes every image test's inputs. | — |
| 18 | Severity threshold | `severity` is the lowest failing level (`UNKNOWN` < `LOW` < `MEDIUM` < `HIGH` < `CRITICAL`; default `HIGH`), checked at analysis. Trivy reports every severity and the driver decides, so findings below the threshold are counted in the log, not hidden. | — |
| 19 | DB age | Each test log prints every data artifact's repository, digest, build time and age in days. For the DBs that is `metadata.json`'s `UpdatedAt`; for the checks bundle, the manifest's `created` annotation and its version. `bazel run @rules_trivy//:db_info` prints the same. A wall-clock age limit that fails tests was left out, for the same caching reason as #17. | — |
| 20 | Bumping the data | Consumers: `bazel run @rules_trivy//:db_latest` resolves each tag (`trivy-db:2`, `trivy-java-db:1`, `trivy-checks:2`) to its current digest and prints `trivy.db(digest = …)` lines for `MODULE.bazel`. Maintainers: `tools/update_db.sh [kinds]` rewrites `DATA` in `private/versions.bzl` with the same code (`private/trivy.py latest`). A new DB can change what the fixtures report, so the in-tree tests are run after a bump. | — |
| 21 | Fixtures | No base image and nothing pulled. Each test image is one layer built with tar.bzl's `tar` (mtree lines, fixed owners and times) and rules_oci's `oci_image`: an Alpine 3.22 `os-release` and an apk `installed` database naming one zlib version. 1.3.1-r2 has two HIGH and two MEDIUM CVEs in the pinned DB; 1.4-r0 has none. The Java image adds a 436-byte jar, generated from a `pom.properties` naming log4j-core 2.14.1. Layers are 6–8 KB. They exercise every case on a real rules_oci image, including an `oci_image_index`. They are tied to the pinned DB: a DB bump that adds a zlib CVE changes the expected counts. | — |
| 22 | Exit codes and reports | 0 pass; 1 findings at or above the threshold, or an expired entry; 2 rules_trivy or Trivy failed (malformed ignore file, Trivy error, nothing recognised, a missing input). Before Trivy runs, the driver checks every input is in the runfiles: the Trivy binary, the image or each src, the ignore file, and each data artifact's `info.json` and cache files (`trivy.db`, `metadata.json`, `bundle.tar.gz`). A missing one fails with one line naming it (`the vulnerability DB is missing: external/+trivy+trivy_db/db/trivy.db`), not Trivy's `unable to initialize archive image` or a traceback (which also exited 1, as if there were findings) (#1). JUnit has one failing case per finding (`$XML_OUTPUT_FILE`), and Trivy's JSON report goes to the undeclared outputs. | rules_gitleaks |
| 23 | Release archive | `tests/` (dev-only rules_oci, tar.bzl, rules_shell) and `tools/` are `export-ignore`, so `@rules_trivy//...` loads for consumers. CI's `consumer` job checks this from the commit's `git archive`, along with the tag behaviours (#2, #4) and a root data pin. | rules_argocd #19, rules_gitleaks v0.2.1 |
| 24 | Host requirements | `python3` 3.8+ (standard library only) on the host, as for rules_gitleaks. Linux and macOS, amd64 and arm64; validated on Linux x86_64. | rules_gitleaks |

## Do old DB digests survive? (#6)

The risk was that aquasecurity prunes old `trivy-db` manifests and blobs, so a digest pinned today would stop downloading in a few days or weeks. If so, a pin would need snapshot mirroring, for example to this repository's release assets. Checked on 2026-11-16:

- **The registry tag list** (`/v2/aquasecurity/trivy-db/tags/list`) shows only `1`, `2` and `latest`, so old digests aren't reachable by tag.
- **The public package page** (`github.com/aquasecurity/trivy-db/pkgs/container/trivy-db/versions`, untagged filter) lists **12,131 untagged versions** over 243 pages. Page 1 is from hours ago, page 2 from 7–12 days ago, page 20 from 4 months ago, page 100 from almost 2 years ago and page 243 from about 5 years ago. The GitHub API listing needs `read:packages`, which wasn't available.
- **Fetching by digest, anonymously:**

  | Manifest digest | Created | Manifest | Layer |
  |---|---|---|---|
  | `sha256:4e84a691e708…` | 2026-11-04 (12 days) | 200 | 206 (range) |
  | `sha256:974028858d9f…` | 2026-07-16 (4 months) | 200 | **full download, 105,278,501 bytes, sha256 matches `917c63aae2b9…`**; `metadata.json` `UpdatedAt` 2026-07-16 |
  | `sha256:fe1bdfb88fda…` | 2025-02-06 (21 months) | 200 | 206 (range) |
  | `sha256:9ccb3409471e…` | ~2021 (5 years) | 200 | 206 (range) |

So nothing is pruned on a timescale that matters to a pin, and rules_trivy fetches straight from GHCR. Two caveats remain:
- **No guarantee.** This is observed behaviour, not a retention policy aquasecurity documents. If it changes, the `repository` attribute (#6) points pins at a mirror holding the same digests.
- **No snapshot assets.** There are none to upload.

## Not done

- **Secret, license and SBOM scanning,** and `trivy fs` / `trivy repo` scans. The scanners are `vuln` (images) and misconfiguration (config) only. `extra_args` can add Trivy flags.
- **VEX documents and `--ignore-policy`** (Rego). The ignore file is the one suppression mechanism, so every suppression has a reason and an expiry.
- **A pulled image** (rules_oci `oci.pull`) as `image`: its repository provides an OCI layout, which should work like an `oci_image`'s, but it wasn't tested.
- **An age limit for the DB** that fails tests; see #19.
- **Windows.**
